# 多联系人调度修复

## 原因

此前面板使用一个工作线程和全局 busy 标记，模型调用、轮询、输入、发送全部互斥。一位联系人等待模型时，另一位联系人不能进入模型请求，轮询也暂停。此前测试按顺序投递两人的消息，没有验证真实的任务重叠。

本地记录还发现 shanyan 的一条旧版 `c_review`：已有原生出站证据，但未点击旧版人工验收按钮，调度器因此阻塞后续消息。

## 修改

- 模型请求使用两个工作线程，不同联系人可同时请求；每个联系人最多处理一条在途消息，后续消息按顺序等待出站确认后使用更新的独立历史。
- 微信 UIA 和原生 SQLite 快照继续由一个专用工作线程访问。模型等待不会占用它，消息轮询可以继续。输入、发送及出站检查仍依次执行，出站证据等待最长约 12 秒，此期间其他原生操作需要排队。
- GUI 和验收数据库只在主线程更新。忙碌状态区分原生操作与各联系人的模型任务；停止后的旧任务回调不能继续输入或发送。
- 单条模型请求失败只结束该样本，其他联系人继续。原生操作故障或发送不确定仍停止整个 Bot，不自动重发。
- 已有原生出站证据的旧 `c_review` 不再阻塞新消息，不修改原有人工验收标记；`uncertain` 记录继续阻塞。旧待人工验收记录仍不计入已通过验收的模型历史。
- 多联系人一轮读取全部成功后才提交游标；暂时性快照冲突留待下一轮读取，避免后一个联系人的读取失败导致前一个联系人新消息被跳过。

## 回归验证

新增真实 Tk 调度器测试，使用模拟微信与模型，并用线程事件控制两条请求的重叠：

1. A 的模型持续等待，B 经轮询进入、完成模型回复和发送，且两个模型确实位于不同线程。
2. A 的第二条消息不会提前请求；A、B 后续请求分别只带本联系人的已发送历史。
3. 停止后释放正在等待的模型任务，确认不再输入或发送。
4. A 模型超时不停止 B，也不会把 A 的失败回复写入历史。
5. 已验证出站的旧记录不阻塞新消息；所有原生操作仍在同一工作线程。
6. 第二联系人快照冲突后重读，两人的新消息均只交付一次。

完整回归最终为 **170 项通过**，Ruff 检查通过。首次完整运行有一项在创建 Tk 窗口时报告主题文件不可读取；检查文件实际存在后重新完整运行，170 项全部通过，未跳过该测试。

这些是模拟并发回归，不代表已经完成两个真人联系人连续来信的实测。重启新版面板，保持两位白名单独立窗口打开并启动 Bot 后，可以同时发消息观察各标签页的消息、回复及出站证据。
